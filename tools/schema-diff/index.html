Важно

Инструмент сравнивает определения структуры базы данных из SQL-скриптов. Он не подключается к реальным базам данных и не проверяет фактическое состояние таблиц, наличие данных и существование объектов на сервере.

Сгенерированный скрипт миграции необходимо проверить перед выполнением. Удаление таблиц и столбцов может привести к безвозвратной потере данных, а изменение типов, ограничений и индексов может вызвать ошибки или блокировки.

Сравнивайте схемы, подготовленные для одного и того же диалекта SQL. Если скрипты содержат конструкции, которые инструмент не поддерживает, они будут отмечены как требующие ручной проверки.

Что такое SQL Schema Diff?

SQL Schema Diff - это инструмент сравнения двух версий структуры реляционной базы данных. Он анализирует определения таблиц, столбцов, индексов и ограничений, определяет различия между исходной и целевой схемами и помогает подготовить SQL-скрипт для изменения структуры базы данных.

Такое сравнение полезно при разработке приложений, обновлении структуры базы данных, проверке миграций и подготовке изменений к выпуску новой версии программного продукта.

Вместо ручного поиска различий между длинными CREATE TABLE инструмент строит структурное представление обеих схем и сопоставляет объекты по их именам и определениям.

Как работает сравнение SQL-схем?

Сравнение выполняется в три последовательных этапа.

Разбор SQL

Инструмент анализирует CREATE TABLE и другие поддерживаемые определения DDL. Из SQL-кода извлекаются имена таблиц, столбцы, типы данных, значения по умолчанию, индексы и ограничения. Результатом становится структурная модель каждой схемы.

Сравнение структур

Таблицы сопоставляются по именам, а столбцы и индексы - по соответствующим идентификаторам и определениям. Инструмент определяет добавленные, удалённые и изменённые объекты, не учитывая обычные различия форматирования SQL.

Генерация миграции

Обнаруженные изменения преобразуются в последовательность SQL-команд, соответствующих выбранному диалекту. Потенциально разрушительные операции отдельно отмечаются и требуют проверки перед включением в исполняемую миграцию.

Добавление и удаление столбцов

Если столбец присутствует только в новой схеме, инструмент определяет его как добавленный. Для него можно сформировать команду ALTER TABLE ... ADD COLUMN.

Если столбец существует только в старой схеме, он считается удалённым. Такая операция потенциально опасна, поскольку вместе со столбцом удаляются содержащиеся в нём данные.

ALTER TABLE customers
ADD COLUMN phone VARCHAR(20);

Изменение типов данных и ограничений

Schema Diff сравнивает не только имена столбцов, но и их структурные свойства. Например, изменение длины VARCHAR, точности DECIMAL, обязательности поля или значения DEFAULT может потребовать изменения существующего определения столбца.

-- Старая структура
name VARCHAR(100) NOT NULL

-- Новая структура
name VARCHAR(200) NOT NULL

Инструмент должен отдельно показывать, какое именно свойство изменилось. Это помогает разработчику понять смысл миграции, а не просто увидеть общую команду MODIFY COLUMN.

Изменение типа данных не всегда безопасно. Сужение диапазона или длины может привести к потере информации, а изменение обязательности поля может завершиться ошибкой при наличии существующих NULL-значений.

Сравнение индексов и ограничений

Индексы влияют на доступ к данным и производительность запросов. При сравнении схем важно учитывать не только имя индекса, но и его тип, уникальность и последовательность индексируемых столбцов.

Кроме индексов, структурное сравнение может включать первичные и внешние ключи, ограничения уникальности и CHECK. Изменение таких объектов влияет на целостность данных и допустимые операции с таблицами.

Перед удалением или изменением ограничения проверьте, какие части приложения и другие объекты базы данных зависят от него.

Что происходит при удалении таблицы или столбца?

Удаление таблицы или столбца может привести к безвозвратной потере данных. В отличие от обычного изменения формата SQL, такая операция меняет саму структуру хранения информации.

По этой причине инструмент отдельно отмечает удаляемые объекты и не включает соответствующие DROP TABLE и DROP COLUMN в исполняемую часть миграции по умолчанию.

Перед включением подобных операций проверьте резервные копии, зависимости, запросы приложения, отчёты и другие объекты, использующие удаляемые данные.

Почему изменение схемы может быть опасным?

Даже корректная с точки зрения синтаксиса миграция не обязательно безопасна для рабочей базы данных. Результат зависит от объёма данных, версии СУБД, ограничений, индексов, механизмов блокировки и особенностей хранения.

Например, добавление столбца с ограничением NOT NULL может оказаться невозможным без предварительного заполнения значений в существующих строках. Создание уникального индекса может завершиться ошибкой при наличии повторяющихся данных.

Изменение типа большого столбца может вызвать длительную перестройку таблицы или блокировку операций. Конкретное поведение зависит от СУБД и версии.

Сравнение SQL-схем и реальные базы данных: в чём разница?

SQL Schema Diff сравнивает два предоставленных определения структуры. Он не подключается к серверам, не получает сведения из системных каталогов и не проверяет фактическое содержимое таблиц.

Если в одном SQL-скрипте отсутствует индекс, это означает, что его нет в предоставленном определении схемы. Однако инструмент не может самостоятельно установить, существует ли этот индекс в реальной базе данных.

Для сравнения реального состояния баз данных сначала получите актуальные определения DDL из каждой среды, а затем передайте их инструменту.

Рекомендуемый порядок работы с SQL Schema Diff

  1. Получите текущую схему.

    Подготовьте SQL-описания действующих таблиц из исходной базы данных.

  2. Подготовьте целевую схему.

    Добавьте обновлённые определения таблиц, столбцов, индексов и ограничений.

  3. Выберите диалект SQL.

    Укажите СУБД, для которой предназначены схемы и будущая миграция.

  4. Сравните структуры.

    Нажмите «Сравнить схемы», чтобы получить список обнаруженных изменений.

  5. Изучите различия.

    Проверьте изменения типов, ограничений, индексов и удаляемых объектов.

  6. Проверьте миграционный скрипт.

    Убедитесь, что операции выполняются в правильном порядке и соответствуют целевой СУБД.

  7. Протестируйте миграцию.

    Запустите скрипт на тестовой копии базы данных и оцените его влияние на реальные данные.

Что проверить перед выполнением миграции в production?

Сгенерированный SQL - это основа для подготовки миграции, но не гарантия её безопасного выполнения. Перед применением изменений в рабочей базе данных проверьте следующие условия.

Создайте резервную копию

Перед изменением структуры убедитесь, что актуальная резервная копия базы данных создана и её можно восстановить.

Проверьте существующие данные

Убедитесь, что новые ограничения NOT NULL, UNIQUE и FOREIGN KEY совместимы с данными, которые уже хранятся в таблицах.

Оцените влияние на большие таблицы

Изменение типов, создание индексов и удаление столбцов может потребовать длительных операций и повлиять на доступность базы данных.

Проверьте зависимости

Перед удалением столбцов или таблиц проверьте представления, внешние ключи, триггеры, запросы приложения и ORM-модели.

Протестируйте миграцию

Выполните скрипт на тестовой копии базы данных с объёмом данных, близким к рабочей среде.

Подготовьте план восстановления

Продумайте, как восстановить структуру и данные в случае ошибки. Не рассчитывайте на обычный ROLLBACK для операций DDL, поскольку поведение транзакций зависит от СУБД.

Часто задаваемые вопросы

Какие SQL-диалекты поддерживает инструмент?
Инструмент поддерживает только те диалекты, для которых реализованы разбор структуры, сравнение объектов и генерация корректных миграционных команд. Доступные варианты указаны в селекторе диалекта. Синтаксис миграций может различаться между СУБД.
Какие SQL-объекты можно сравнивать?
Основная область сравнения - таблицы, столбцы, индексы и поддерживаемые ограничения. Возможности сравнения зависят от реализованного набора DDL-конструкций выбранного диалекта.
Можно ли сравнить сразу несколько таблиц?
Да. Вы можете вставить несколько определений CREATE TABLE в каждый редактор. Инструмент сопоставит таблицы по именам и покажет изменения отдельно для каждой из них.
Обнаруживает ли инструмент переименование столбцов?
Переименование может выглядеть как удаление одного столбца и добавление другого. Без дополнительной информации невозможно всегда достоверно определить, что это именно переименование. Поэтому такие изменения необходимо проверить вручную.
Учитывается ли порядок столбцов?
Изменение порядка объявлений столбцов само по себе не считается структурным изменением в стандартном режиме сравнения. Инструмент ориентируется на имена и определения объектов.
Генерирует ли инструмент ALTER TABLE?
Да. На основе обнаруженных различий инструмент формирует SQL-команды для изменения структуры, если соответствующие операции поддерживаются выбранным диалектом. Некоторые изменения могут потребовать ручной подготовки миграции.
Удаляются ли данные при сравнении схем?
Нет. Инструмент не подключается к базе данных и не выполняет SQL. Он только анализирует определения структуры и формирует текст миграции.
Почему удаление столбцов и таблиц отключено по умолчанию?
Потому что DROP COLUMN и DROP TABLE могут привести к безвозвратной потере данных. Эти команды отображаются отдельно и включаются в миграцию только после явного выбора пользователя.
Проверяет ли инструмент миграцию перед выполнением?
Нет. Синтаксический анализ схемы и генерация миграции не подтверждают, что скрипт успешно выполнится на реальной базе данных. Проверьте его на тестовой среде.
Отправляются ли мои SQL-схемы на сервер?
Нет. Разбор, сравнение и генерация SQL выполняются непосредственно в браузере. Содержимое схем не отправляется на сервер и не сохраняется в базе данных приложения.
Можно ли сравнить две реальные базы данных напрямую?
Нет. Инструмент работает с предоставленными SQL-описаниями структуры, а не с подключениями к базам данных. Сначала экспортируйте DDL из обеих сред, затем вставьте его в редакторы.

Минифицировать SQL

Хотите научиться самостоятельно проектировать базы данных?

Сравнение схем помогает находить изменения, но правильное проектирование базы данных начинается с понимания таблиц, связей, типов данных, ключей и ограничений целостности.

На курсах SQL с нуля до результата вы последовательно изучите структуру реляционных баз данных, создание таблиц, связи между ними, запросы и практическую работу с SQL.
