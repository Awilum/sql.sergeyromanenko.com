## Что такое ER-диаграмма?

ER-диаграмма (Entity-Relationship Diagram) - это визуальное представление структуры реляционной базы данных. Она показывает сущности, соответствующие таблицам, их атрибуты, первичные и внешние ключи, а также связи между таблицами.

ER-диаграммы помогают понять, как организованы данные в приложении, какие таблицы зависят друг от друга и каким образом связанные записи объединяются при выполнении SQL-запросов.

Вместо просмотра большого количества CREATE TABLE разработчик получает наглядную модель базы данных, которую можно использовать при проектировании, анализе и документировании структуры.

## Как работает генератор ER-диаграмм?

Инструмент анализирует предоставленные SQL-описания таблиц, извлекает имена объектов, столбцы, типы данных, ограничения и внешние ключи. Затем на основе полученной структуры строится граф таблиц и связей между ними.

Каждая таблица отображается в виде отдельного блока. Внутри блока перечисляются столбцы, их типы данных и ключевые характеристики. Между таблицами отображаются линии, представляющие явно определённые связи.

Положение таблиц и соединяющих их линий рассчитывается автоматически. Пользователь может увеличивать и уменьшать масштаб, перемещаться по большой диаграмме и экспортировать результат.

## Первичные и внешние ключи в ER-диаграммах

Первичный ключ (PRIMARY KEY) однозначно идентифицирует запись в таблице. Он может состоять из одного или нескольких столбцов.

Внешний ключ (FOREIGN KEY) задаёт ссылочную зависимость между таблицами. Например, столбец orders.customer_id может ссылаться на customers.id, если соответствующее ограничение объявлено в SQL.

Уникальные ключи (UNIQUE) позволяют определить поля или комбинации полей, значения которых не должны повторяться. Эта информация также важна для определения возможной кардинальности связей.

## Типы связей между таблицами

### Один-к-одному (1:1)

Одна запись первой таблицы может соответствовать не более чем одной записи второй таблицы. Такое отношение часто используется для хранения дополнительных сведений о пользователе или отдельной части сущности. Для подтверждения ограничения необходимо учитывать UNIQUE или первичный ключ внешнего столбца.

### Один-ко-многим (1:N)

Одна запись родительской таблицы может быть связана с несколькими записями дочерней таблицы. Например, один клиент может иметь несколько заказов. Это один из наиболее распространённых вариантов связей в прикладных базах данных.

### Многие-ко-многим (N:M)

Несколько записей одной таблицы могут быть связаны с несколькими записями другой таблицы. В реляционной модели такое отношение обычно реализуется через промежуточную таблицу с двумя внешними ключами.

## Как реализуется связь многие-ко-многим?

Для реализации отношения многие-ко-многим обычно создаётся отдельная таблица, содержащая внешние ключи на обе связанные сущности.

```sql
CREATE TABLE students (
    id BIGINT PRIMARY KEY
);

CREATE TABLE courses (
    id BIGINT PRIMARY KEY
);

CREATE TABLE student_courses (
    student_id BIGINT NOT NULL,
    course_id BIGINT NOT NULL,
    PRIMARY KEY (student_id, course_id),
    FOREIGN KEY (student_id) REFERENCES students(id),
    FOREIGN KEY (course_id) REFERENCES courses(id)
);
```

В ER-диаграмме такая модель отображается как две связи один-ко-многим: от students к student_courses и от courses к student_courses. В совокупности они описывают отношение многие-ко-многим.

## Почему названий столбцов недостаточно для определения связи?

Название customer_id может указывать на предполагаемую связь с таблицей customers, но само по себе не создаёт ограничение ссылочной целостности.

Связь считается объявленной в структуре базы данных только тогда, когда в SQL определён соответствующий FOREIGN KEY или другая поддерживаемая эквивалентная конструкция.

Поэтому генератор строит подтверждённые связи по явным ограничениям, а не пытается самостоятельно угадывать отношения на основе названий полей. Такой подход предотвращает появление ложных связей на диаграмме.

## Самоссылочные связи в базе данных

```sql
CREATE TABLE categories (
    id BIGINT PRIMARY KEY,
    name VARCHAR(100) NOT NULL,
    parent_id BIGINT,
    FOREIGN KEY (parent_id) REFERENCES categories(id)
);
```

Самоссылочная связь возникает, когда столбец таблицы ссылается на другую запись этой же таблицы. Такая структура часто используется для иерархий категорий, организационных подразделений и древовидных данных.

## Как поделиться ER-диаграммой с коллегами?

Готовую ER-диаграмму можно отправить коллегам или клиентам по ссылке. Получателю не требуется открывать исходный SQL-редактор, чтобы просмотреть визуальную структуру базы данных.

Инструмент создаёт ссылку-снимок, содержащую сжатую копию SQL-схемы. Такая ссылка открывает сохранённую версию диаграммы и не обновляется автоматически после изменений в редакторе.

Ссылка создаётся только по явному действию пользователя. Не следует размещать в открытом доступе конфиденциальные схемы, имена внутренних таблиц и сведения о структуре защищённых систем.

## ER-диаграмма и проектирование базы данных: в чём разница?

ER-диаграмма показывает структуру базы данных и связи между сущностями. Она помогает визуально оценить модель, но сама по себе не проверяет корректность бизнес-логики, производительность запросов или качество физической реализации.

При проектировании необходимо дополнительно учитывать нормализацию, типы данных, индексы, ограничения целостности, объёмы данных и сценарии использования.

Поэтому визуализация является важной частью процесса проектирования, но не заменяет полноценный анализ структуры и поведения базы данных.

## Часто задаваемые вопросы

- **Какие SQL-диалекты поддерживает генератор ER-диаграмм?:** Инструмент поддерживает общие конструкции CREATE TABLE и те особенности MySQL, MariaDB, PostgreSQL и SQLite, для которых реализован и протестирован разбор структуры. Реальные возможности зависят от поддерживаемых DDL-конструкций. Неизвестные особенности диалекта отображаются как предупреждения.
- **Почему инструмент не показывает связь между таблицами?:** Генератор определяет связи по явно объявленным внешним ключам. Если в таблице существует столбец user_id, но в SQL нет FOREIGN KEY, автоматическое соединение с таблицей users не создаётся.
- **Можно ли визуализировать несколько таблиц одновременно?:** Да. Вы можете добавить несколько CREATE TABLE определений в один редактор. Инструмент отобразит распознанные таблицы и установленные между ними связи в общей ER-диаграмме.
- **Поддерживаются ли составные внешние ключи?:** Да, если соответствующая конструкция поддерживается используемым SQL-парсером. Все столбцы составного внешнего ключа должны учитываться как единая связь.
- **Чем отличаются PRIMARY KEY, FOREIGN KEY и UNIQUE?:** PRIMARY KEY однозначно идентифицирует запись, FOREIGN KEY устанавливает ссылку на другую таблицу, а UNIQUE запрещает повторение определённых значений. Все три ограничения содержат важную информацию для построения и анализа ER-диаграммы.
- **Можно ли увидеть отношения многие-ко-многим?:** Такие отношения обычно представлены промежуточной таблицей с двумя или несколькими внешними ключами. Генератор отображает соответствующие связи один-ко-многим, из которых складывается отношение многие-ко-многим.
- **Отправляется ли мой SQL на сервер?:** Построение и экспорт диаграммы выполняются непосредственно в браузере. SQL-схема не отправляется на сервер и не сохраняется в базе данных приложения.
- **Может ли генератор определить связи без FOREIGN KEY?:** Нет. Инструмент не угадывает связи по именам столбцов или похожим названиям таблиц. Для достоверного отображения необходимо объявить FOREIGN KEY или соответствующее поддерживаемое ограничение.
- **Проверяет ли генератор производительность базы данных?:** Нет. ER-диаграмма показывает структуру данных и связи между таблицами, но не анализирует планы выполнения запросов, фактическую нагрузку, стоимость JOIN или производительность индексов.
